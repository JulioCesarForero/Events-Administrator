# Reporte de auditoría MVP e implementación gobernada

## 1) Resumen ejecutivo

La propuesta del MVP para reserva de cupos en mesas es mayoritariamente consistente con la definición de producto y el catálogo de reglas de negocio. El flujo rector está bien establecido:

`código de estudiante -> asistentes -> pago externo -> aprobación comité -> reserva por cupos -> códigos por asistente`.

El análisis detecta inconsistencias documentales puntuales (terminología, contratos API y redacciones ambiguas), pero no fallas estructurales que impidan implementar el MVP de forma segura y escalable.

Veredicto general:

- Consistencia funcional global: **Alta**.
- Viabilidad técnica: **Alta**.
- Riesgo principal: **Ambigüedad documental**, no inviabilidad tecnológica.
- Recomendación: avanzar a implementación con este marco de correcciones normativas.

## 4) Inconsistencias y ambigüedades detectadas

### INC-01 (Alta) - "Un solo uso" vs reingreso del mismo grupo

Problema:

- Se define unicidad por evento para crear grupo.
- En algunos textos UX/plan puede interpretarse que el código no debería permitir reingreso.

Riesgo:

- Implementaciones divergentes entre frontend y backend.
- Fricción para usuarios legítimos que reingresan.

Definición obligatoria:

- Un código de estudiante crea **un solo `AttendeeGroup` por evento**.
- Reingresos posteriores son válidos y deben abrir ese mismo proceso.
- Lo prohibido es crear un segundo grupo con el mismo código en el mismo evento.

---

### INC-02 (Media) - Catálogo API incompleto para legales aceptados

Problema:

- Existe endpoint de consulta de documentos aceptados en secciones narrativas, pero no está consolidado en el catálogo principal de endpoints.

Riesgo:

- Equipos frontend/QA no lo consideran parte del contrato oficial.

Definición obligatoria:

- Incluir formalmente en catálogo:
  - `GET /v1/portal/events/{eventId}/accepted-legal-documents`

---

### INC-03 (Media) - Código de error que puede confundir flujo idempotente de login

Problema:

- `STUDENT_CODE_ALREADY_USED` podría dispararse en un reingreso normal, cuando en realidad debe retornar sesión del mismo grupo.

Definición obligatoria:

- `POST /v1/auth/code-login` es idempotente para el mismo código/evento.
- Debe responder `200` y retornar el grupo existente.
- Solo usar `409` cuando se intente explícitamente crear otro proceso independiente.

---

### INC-04 (Media) - "Código único de reserva" vs "código por asistente"

Problema:

- Mezcla de términos entre identificador de reserva y códigos individuales por participante.

Definición obligatoria:

- `reservationId`: identificador único de reserva (cabecera).
- `reservationCode` por asistente: consecutivo por evento, único por participante confirmado.

---

### INC-05 (Baja) - Diagrama de arquitectura vs decisión de frontend único

Problema:

- Diagrama sugiere dos portales como si fueran dos frontends desplegados separados.

Definición obligatoria:

- Un solo frontend (SPA) con rutas segmentadas:
  - `/portal/*` comprador
  - `/staff/*` comité
- Guards por rol y ámbito de evento.

---

### INC-06 (Media) - Pseudocódigo de liberación simplificado en dominio multi-mesa

Problema:

- Ejemplo de liberación parece asumir una sola mesa.

Definición obligatoria:

- Liberación/movimiento debe iterar todas las filas de `TableReservation` asociadas.
- Recalcular ocupación de manera transaccional y auditable.

---

### INC-07 (Media) - Regla ambigua entre cupos, asistentes y boletas

Problema:

- Texto permite interpretar validaciones alternativas (`asistentes o boletas`).

Definición obligatoria:

- Para confirmar reserva en MVP:
  - `sum(allocations.spotsReserved) == participantes_confirmados_en_reserva`
  - `sum(allocations.spotsReserved) <= boletas_aprobadas_disponibles`

## 5) Definiciones normativas de implementación (obligatorias)

### 5.1 Dominio y consistencia

- Inventario por `LayoutTable` con `table_capacity_limit` y ocupación agregada.
- Sin `Seat` ni `HOLD` en MVP.
- Reserva multi-mesa atómica o rollback total.
- Consentimiento legal obligatorio antes de crear reserva.
- Corrección manual no regenera códigos ya emitidos.

### 5.2 Contratos API y errores

- Contratos versionados en `/v1`.
- Respuestas de error estándar con `code`, `message`, `correlationId`.
- `Idempotency-Key` obligatorio en creación de reservas.
- Login por código idempotente para reingreso.

### 5.3 Reglas temporales

- Cálculo de ventana de 20 días usando zona horaria del evento.
- Cierre de edición de participantes desde ese umbral.

## 6) Viabilidad técnica de stack y decisión recomendada

## Opción A: JWT + FastAPI + React + PostgreSQL

Ventajas:

- Alta productividad para MVP.
- OpenAPI nativo y tipado de payloads con Pydantic.
- Buen soporte para arquitectura por casos de uso.

Riesgos controlables:

- Convenciones arquitectónicas deben imponerse para evitar crecimiento desordenado.

## Opción B: JWT + ASP.NET Core + React + PostgreSQL

Ventajas:

- Excelente robustez empresarial.
- Integración sólida con Azure y tooling de observabilidad.
- EF Core y middleware potente para seguridad y políticas.

Riesgos controlables:

- Curva de entrada mayor para equipos sin experiencia .NET.

## Recomendación técnica

- Ambas opciones son viables.
- Elegir en función de capacidad real del equipo y velocidad de entrega.
- Mantener arquitectura y contratos agnósticos al framework para no comprometer evolución futura.

## 7) Seguridad de implementación y despliegue

### 7.1 Seguridad de aplicación

- TLS obligatorio extremo a extremo.
- JWT separados para comprador y staff (claims y scopes distintos).
- Token de vida corta; refresh token solo para perfiles internos si se necesita.
- RBAC por rol y control de ámbito por evento.
- Rate limiting en login por código y endpoints críticos.
- Validación estricta de archivos (MIME, tamaño, antivirus opcional).
- URLs firmadas para subida/lectura de evidencias.
- No registrar PII sensible completa en logs.

### 7.2 Seguridad de datos

- PostgreSQL con cifrado en reposo.
- Secretos fuera de código (variables de entorno + gestor de secretos).
- Backups automáticos y política de retención.
- Auditoría inmutable para acciones críticas.

## 8) Viabilidad cloud, dockerización y multicloud

### 8.1 Dockerización

Viable y recomendada:

- API en imagen contenedorizada.
- Frontend en imagen estática (nginx) o CDN.
- `docker compose` para local y pruebas.
- PostgreSQL gestionado en cloud para producción.

### 8.2 Multicloud

Viable con diseño por puertos/adaptadores:

- Definir `ObjectStoragePort` en capa de aplicación.
- Adaptadores:
  - AWS S3
  - Azure Blob
  - GCP Cloud Storage
- Selección por configuración (12 Factor), no por condicionales de negocio.

### 8.3 Blob storage

- Evidencias de pago en bucket/contenedor por ambiente.
- Nombres de objeto no predecibles.
- Acceso temporal por URL firmada.
- Trazabilidad de hash y metadatos de archivo.

## 9) Arquitectura objetivo (Clean Architecture)

Capas recomendadas:

1. **Dominio** (entidades/reglas)
2. **Aplicación** (casos de uso)
3. **Infraestructura** (DB, storage, mensajería, terceros)
4. **Interfaces** (REST controllers, DTOs, validación)

Regla:

- Dependencias siempre apuntan hacia adentro.
- El dominio no conoce framework web ni proveedor cloud.

---

## 10) Aplicación de principios SOLID

- **S (Single Responsibility):** separar módulos `Payments`, `Reservations`, `Legal`, `Participants`.
- **O (Open/Closed):** agregar proveedores de storage por adaptadores sin tocar casos de uso.
- **L (Liskov):** adaptadores de storage y repositorios deben respetar contratos.
- **I (Interface Segregation):** interfaces pequeñas por caso de uso, no servicios gigantes.
- **D (Dependency Inversion):** casos de uso dependen de puertos (`Repository`, `StoragePort`, `AuditPort`).

---

## 11) Aplicación de 12 Factor App

- Config en variables de entorno.
- Dependencias explícitas.
- Build/release/run separados.
- Procesos stateless.
- Logs como stream.
- Paridad dev/staging/prod con contenedores.
- Tareas administrativas (migraciones/imports) como procesos one-off.

---

## 12) Aplicación de heurísticas de Nielsen (UX)

- **Visibilidad del estado:** badges claros (`Borrador`, `En revisión`, `Aprobado`, `Rechazado`).
- **Prevención de errores:** bloquear acciones inválidas con causa explícita.
- **Control y libertad:** reenvío de pago rechazado y edición permitida en ventana válida.
- **Consistencia:** lenguaje simple, no exponer estados técnicos en UI pública.
- **Reconocimiento sobre memoria:** resumen de reserva y códigos visibles al reingresar.
- **Ayuda para errores:** mensajes de concurrencia con recarga guiada de disponibilidad.

---

## 13) Riesgos residuales y decisiones pendientes (gobernanza)

1. Política exacta cuando comité aprueba cantidad distinta a la reportada.
2. SLA operativo de revisión de pagos.
3. Detalle legal/auditable visible para reconsulta de aceptación.
4. Política de retención de comprobantes y PII por normativa aplicable.
5. Estrategia formal de recuperación ante desastres (RPO/RTO).

---

## 14) Plan de implementación recomendado (ejecutable)

Fase 1 (base):

- Esqueleto modular backend + esquema de datos.
- Auth comprador/staff + RBAC.
- Importación de estudiantes.

Fase 2 (flujo principal):

- Participantes + pagos + bandeja comité.
- Publicación legal y reconsulta.

Fase 3 (reserva y concurrencia):

- Mapa y reserva multi-mesa atómica.
- Secuencia por asistente e idempotencia.

Fase 4 (hardening):

- Observabilidad, seguridad avanzada, QA de concurrencia, smoke multicloud.

---

## 15) Conclusión del equipo auditor

El MVP es técnicamente factible y estratégicamente correcto para una salida controlada, siempre que se apliquen las definiciones normativas de este reporte. La arquitectura propuesta permite crecer de forma mantenible y escalable, con base sólida para evolución multicloud y operación gobernada.

La principal acción inmediata no es rediseñar el producto, sino cerrar ambigüedades documentales y convertir estas reglas en criterios obligatorios de desarrollo, pruebas y despliegue.
