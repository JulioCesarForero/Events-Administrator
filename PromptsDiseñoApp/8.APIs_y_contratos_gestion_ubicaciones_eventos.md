## 2. Método HTTP

- `GET`: consulta y lectura.
- `POST`: creación o acciones con cambio de estado.
- `PATCH`: edición parcial de recursos mutables.
- `PUT`: actualización integral de configuración estable.

---

## 3. Propósito de cada endpoint

### Autenticación por código

`POST /v1/auth/code-login`  
Valida el `codigo_estudiante` contra el padrón importado del evento y genera una sesión de comprador. Es idempotente por `studentCode + eventId`: si el código ya fue usado en ese evento, responde `200` y reabre el mismo proceso existente sin crear un nuevo grupo.

### Importación de estudiantes

`POST /v1/events/{eventId}/student-imports`  
Registra una carga de archivo CSV o Excel y dispara su procesamiento.

### Documentos legales

`GET /v1/events/{eventId}/legal-documents`  
Consulta la política de tratamiento de datos y los términos y condiciones vigentes o históricos del evento.

`GET /v1/portal/events/{eventId}/accepted-legal-documents`  
Permite al comprador consultar nuevamente la versión exacta de la política y los términos aceptados en su reserva.

`POST /v1/events/{eventId}/legal-documents`  
Crea una nueva versión de política o términos.

### Pagos

`POST /v1/groups/{groupId}/payments`  
Crea un pago en estado `DRAFT`.

`POST /v1/payments/{paymentId}/submit`  
Pasa el pago a `PENDING_APPROVAL`.

`POST /v1/payments/{paymentId}/approve`  
Pasa el pago a `APPROVED`.

`POST /v1/payments/{paymentId}/reject`  
Pasa el pago a `REJECTED`.

### Reservas

`POST /v1/events/{eventId}/reservations`  
Crea una reserva definitiva por cupos en mesa para un grupo con pago aprobado y consentimiento legal aceptado.

### Mapa

`GET /v1/events/{eventId}/map`  
Devuelve la proyección del layout con disponibilidad agregada por mesa.

## 5. Códigos de error

| HTTP | code | Uso |
|------|------|-----|
| 400 | `INVALID_PAYLOAD` | Esquema o formato inválido |
| 401 | `UNAUTHENTICATED` | Sin autenticación |
| 403 | `FORBIDDEN` | Sin permisos |
| 404 | `NOT_FOUND` | Recurso inexistente |
| 409 | `TABLE_CAPACITY_CONFLICT` | La mesa ya no tiene cupos suficientes |
| 409 | `PAYMENT_ALREADY_REVIEWED` | El pago ya fue aprobado o rechazado |
| 409 | `STUDENT_CODE_ALREADY_USED` | Solo cuando se intenta explícitamente crear un segundo proceso independiente en el evento |
| 422 | `STAGE_LIMIT_EXCEEDED` | Excede límite de preventa o venta |
| 422 | `PAYMENT_NOT_APPROVED` | El mapa o la reserva requieren pago aprobado |
| 422 | `MISSING_PAYMENT_EVIDENCE` | Falta evidencia en pago digital |
| 422 | `LEGAL_ACCEPTANCE_REQUIRED` | Falta aceptar política y términos |
| 422 | `LEGAL_DOCUMENTS_NOT_PUBLISHED` | El evento no tiene política o términos vigentes |
| 422 | `PARTICIPANT_EDIT_WINDOW_CLOSED` | Ya no puede editar participantes el comprador |
| 422 | `PARTICIPANTS_INCOMPLETE` | Faltan datos de asistentes |
| 422 | `RESERVATION_EXCEEDS_APPROVED_TICKETS` | Excede boletas aprobadas |
| 422 | `RESERVATION_OR_REFUND_NOT_SUPPORTED` | Cancelación o devolución fuera de la app |

### Formato de error sugerido

```json
{
  "error": {
    "code": "TABLE_CAPACITY_CONFLICT",
    "message": "La mesa ya no tiene cupos suficientes para completar la reserva.",
    "correlationId": "req-123"
  }
}
```

## 6. Reglas de validación

- `studentCode` debe existir en el padrón del evento.
- `POST /v1/auth/code-login` debe retornar `200` y el grupo existente cuando sea reingreso del mismo `studentCode` en el mismo `eventId`.
- `studentCode` no puede iniciar un segundo uso independiente dentro del mismo evento; solo en ese caso corresponde `409 STUDENT_CODE_ALREADY_USED`.
- No se puede enviar un pago a revisión sin asistentes completos.
- En preventa no se puede superar `4` boletas.
- En venta general no se puede superar `3` boletas.
- Las ediciones de participantes por comprador se bloquean cuando faltan 20 días o menos para el evento, calculados en la zona horaria del evento.
- El evento debe tener política y términos publicados antes de aceptar reservas.
- Un pago digital debe tener evidencia antes de pasar a revisión.
- Un pago en efectivo debe incluir foto del recibo de caja cuando es registrado por el comité.
- Un comprador no puede editar un pago aprobado.
- El mapa no puede habilitarse sin `APPROVED`.
- La reserva no puede confirmarse sin aceptación explícita de política y términos.
- Una reserva no puede superar:
  - los cupos libres de cada mesa involucrada,
  - las boletas aprobadas del grupo.
- La suma de asignaciones multi-mesa debe coincidir con la cantidad de asistentes o cupos aprobados que se están reservando.

## 7. Consideraciones de seguridad

- TLS obligatorio.
- Tokens separados para comprador y staff.
- Autorización por rol y por ámbito del evento.
- URLs firmadas o mediadas para subir y leer evidencias.
- Logs sin exponer tokens ni datos sensibles innecesarios.
- Rate limit en login por código y acciones críticas.

## 8. Reglas de idempotencia

| Endpoint | Clave | Comportamiento |
|----------|-------|----------------|
| `POST /v1/auth/code-login` | `studentCode + eventId` | Reingreso idempotente: `200` y grupo existente |
| `POST /v1/events/{eventId}/reservations` | `Idempotency-Key` | Evita duplicar reservas por reintento |
| `POST /v1/payments/{paymentId}/approve` | `Idempotency-Key` opcional | Evita doble aprobación accidental |
| `POST /v1/events/{eventId}/cash-payments` | referencia manual única | Evita duplicar registro de efectivo |
| `POST /v1/events/{eventId}/student-imports` | hash o referencia del archivo | Evita reimportaciones accidentales |

- `PAYMENT_SUBMITTED`
- `PAYMENT_APPROVED`
- `PAYMENT_REJECTED`

- `TABLE_RESERVATION_RELEASED`

## 10. Recomendaciones para versionamiento

- Prefijo `/v1`.
- Mantener estabilidad de nombres y códigos de error.
- Los cambios incompatibles deben ir a `/v2`.
- Publicar OpenAPI por versión.
- Preferir agregar campos opcionales antes que romper contratos existentes.

---

Este documento sustituye el contrato anterior basado en `seatIds`, `holds`, `confirm` y webhooks como flujo central. La API oficial del MVP se basa en importación, revisión manual y reserva por mesa.
