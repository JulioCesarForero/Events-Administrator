# Pruebas, riesgos y criterios de aceptación — MVP reserva de cupos en mesas

Documento de calidad alineado con el MVP vigente.

---

## 1. Riesgos funcionales críticos

| ID | Riesgo | Impacto |
|----|--------|---------|
| RF-01 | Pago aprobado incorrectamente | Reserva indebida |
| RF-02 | Reserva sin pago aprobado | Ruptura del flujo de negocio |
| RF-03 | Doble asignación de la misma mesa | Sobreocupación |
| RF-04 | Grupo reserva más cupos que sus boletas aprobadas | Inconsistencia comercial |
| RF-05 | El mapa se habilita antes de tiempo | Mala experiencia y errores |
| RF-06 | Ajuste manual rompe capacidad | Riesgo operativo el día del evento |
| RF-07 | Edición indebida de participantes después del corte de 20 días | Riesgo operativo y de cumplimiento |
| RF-08 | Códigos secuenciales mal asignados o duplicados | Trazabilidad incorrecta por asistente |
| RF-09 | Reserva sin aceptación válida de política y términos | Riesgo jurídico y de cumplimiento |
| RF-10 | Reutilización indebida de un código de estudiante creando un segundo proceso en el mismo evento | Acceso inconsistente o duplicado |

## 5. Casos de prueba de concurrencia

| ID | Caso | Resultado esperado |
|----|------|-------------------|
| TC-CONC-001 | Dos reservas simultáneas sobre una mesa con cupos para una sola | Solo una se confirma |
| TC-CONC-002 | Dos reservas simultáneas consumiendo el último cupo disponible | Solo una actualiza el contador |
| TC-CONC-003 | Reserva multi-mesa con conflicto en una de las mesas | Toda la operación falla sin estado parcial |
| TC-CONC-004 | Movimiento manual y reserva pública al mismo tiempo | El backend mantiene consistencia |
| TC-CONC-005 | Reintento con misma `Idempotency-Key` | No duplica reserva |
| TC-CONC-006 | Dos reservas exitosas concurrentes generan códigos secuenciales | No se duplican códigos dentro del evento |

## 9. Criterios de aceptación por módulo

| Módulo | Criterio |
|--------|----------|
| Importación | Debe cargar estudiantes válidos y reportar errores |
| Login por código | Solo acceden códigos vigentes del evento |
| Asistentes | Deben validarse campos obligatorios |
| Asistentes | Deben respetar la ventana de edición hasta 20 días antes del evento |
| Pagos | Deben seguir el ciclo `DRAFT -> PENDING_APPROVAL -> APPROVED/REJECTED` |
| Pagos | El efectivo debe incluir foto del recibo de caja |
| Legal | Debe existir CRUD y publicación de política de datos y términos del evento |
| Bandeja comité | Debe permitir revisar y decidir pagos con trazabilidad |
| Mapa | Debe mostrar disponibilidad agregada por mesa |
| Reservas | Deben respetar cupos, boletas aprobadas y atomicidad multi-mesa |
| Reservas | Deben emitir códigos correlativos por asistente sin duplicidad |
| Reservas | Deben exigir aceptación explícita de política y términos antes de confirmar |
| Ajustes manuales | Deben respetar consistencia y dejar auditoría |

## 10. Recomendaciones para automatización de pruebas

### Prioridad de automatización

1. pruebas de API para importación, pagos y reservas,
2. pruebas de concurrencia sobre reserva,
3. pruebas E2E del flujo comprador y comité,
4. validaciones de auditoría.

### Herramientas sugeridas

- pruebas unitarias para reglas puras,
- pruebas de integración con base de datos real o contenedores,
- pruebas E2E con navegador,
- pruebas de concurrencia con scripts paralelos.

### Gates mínimos

- no liberar reserva sin pruebas de concurrencia verdes,
- no liberar pagos sin flujo de aprobación cubierto,
- no liberar piloto sin smoke E2E completo.

---

Este documento reemplaza la estrategia previa basada en sillas, `HOLD`, expiración temporal y confirmación por webhook. La calidad del MVP vigente debe centrarse en importación, aprobación manual y reserva por mesa.
